# Конвенции пульта запуска

Общий документ для обоих агентов проекта (Claude Code и Kimi Code). Слэш-команды
`/board`, `/sessions` и их kimi-двойники — тонкие обёртки над этим файлом; вся суть здесь,
чтобы правила не разъезжались между двумя наборами скиллов.

---

## 1. Источник истины

**Бэклог — GitHub Issues** на `AutonomaCo/promelectron` + доска GitHub Project.
`ai-launcher/BOARD.md` — **витрина** этого бэклога.

- Пункта нет в Issues → его нет вообще. Промпт без issue — потерянная работа: его не увидит
  ни `/backlog-list`, ни сверка, ни коллега.
- Пункт, существующий только на борде, — источник будущей путаницы. При сверке такой пункт
  либо заводится issue, либо убирается с борда, и об этом говорится владельцу вслух.
- `.agent/BACKLOG.md`, `.agent/BLOCKERS.md` — **человеческий спринт-планер и журнал блокеров**,
  отдельный артефакт. Борд может брать оттуда контекст, но не считает их бэклогом и не
  правит их вместо issue.

---

## 2. Замки

Замок — **область файлов**. Два пункта с одним замком параллельно **не идут**: это не
осторожность, а единственный способ не разгребать конфликты в чужой ветке.

| Замок | Что покрывает |
|---|---|
| `backend` | `backend/**` — FastAPI, сервисы, модели, Alembic, pytest |
| `frontend` | `frontend/src/**`, компоненты, композаблы, vitest |
| `e2e` | `frontend/e2e/**` — Playwright-спеки и хелперы |
| `infra` | `infra/**`, `.github/workflows/**`, Helm, SOPS, деплой |
| `docs` | `docs/**`, `README.md`, `PROJECT_CONTEXT.md`, `ARCHITECTURE.md` |
| `harness` | `.claude/**`, `.kimi-code/**`, `ai-launcher/**`, `Makefile`, `scripts/**` |
| `none` | пункт не трогает репозиторий (доступы, настройка внешнего сервиса) |
| `all` | меняет правила игры — идёт **один**, без соседей в волне |

Пункт берёт **все** замки, чьи файлы трогает: фронт-фича, которая правит и компонент, и
Playwright-спеку, занимает `frontend`+`e2e`. Не занижай — занижённый замок и есть тот самый
конфликт.

Замок `e2e` выделен из `frontend` намеренно: починки флаки-тестов идут потоком и почти
никогда не пересекаются с продуктовой фронт-работой по файлам.

## 3. Форма пульта

Пульт читают глазами и с него запускают работу — разметка тут часть инструмента, а не
оформление. Пункт выглядит так, и порядок частей не меняется:

````markdown
---

> <a id="i-186"></a>🟢 **#186** · флаки cart-select.spec.js — `lock: e2e` · **свободен**

```bash
make ai PROMPT=ai-launcher/prompts/e2e_186-cart-select-flaky.prompt.txt
```

Два-три абзаца: в чём боль, чем лечится, что уже замерено. Не разбор — выжимка.
````

Обязательное:

- **`---` между пунктами.** Без разделителя описание пункта визуально прилипает к кнопке
  следующего, и абзац про один пункт читается как продолжение другого.
- **Один якорь на пункт, и он уникален.** `id="i-NN"` ставится ровно один раз на файл, из
  Указателя на него ведёт `[#NN](#i-NN)`. Задвоенный якорь не ломает рендер — он молча
  уводит кнопку не туда.
- **Один пункт — одно место.** Пункт не появляется в двух разделах; переехал — старый блок
  удаляется, а не оставляется «пока».
- **Статус в заголовке пункта и статус в Указателе — одна и та же правда.** Они читаются по
  отдельности, поэтому правятся оба.
- **Кнопка только там, где есть промпт.** Нет файла в `prompts/` — пункт идёт в список
  «заведено, но кнопки нет».

Статусы: 🟢 можно · 🟡 можно, но сначала ответ владельца · 🔵 занято · 🔴 нельзя, причина
указана · 💤 припарковано · ✅ закрыто.

🟢 ставится, только если замок реально свободен. Два пункта с одним замком не бывают 🟢
одновременно — второй «в очереди за первым».

### Проверка перед коммитом борда

```bash
python3 scripts/check-board.py            # форма + кнопки + связки промпт↔issue
python3 scripts/check-board.py --offline  # без обращений к GitHub
```

Скрипт ловит: задвоенные якоря, ссылки Указателя в никуда, пункты без разделителя, пункт без
ссылки на GitHub, кнопку без промпта, промпт без кнопки, промпт без issue в шапке, промпт,
ведущий на **закрытый** issue, и issue без блока «Запуск» в теле.

Красный — чинится до коммита: борд правится прямым push'ем в `main`, ревью на нём нет.

## 4. Разделы борда

| Раздел | Что в нём |
|---|---|
| 🧭 Указатель | таблицы по направлениям: ID, о чём пункт, замок, статус |
| 🔒 Замки | кто занят, кто свободен, что с чем делится, что брать следующим |
| 🔵 В работе | пункт → ветка → PR. Строка живёт, пока PR не смержен |
| ⏰ Ждут условия | хвосты, ждущие **события**, а не решения (см. ниже) |
| 🟡 Ждут твоего решения | что нельзя двигать без ответа владельца |
| Пункты | сами блоки с кнопками, сгруппированные по направлениям |

### ⏰ Ждут условия

Не «ждут твоего решения» и не «только ты» — **ждут события**. Решать нечего, доступ есть,
надо дождаться: реальных ключей платёжки, ответа внешнего сервиса, окна выката.

Такие хвосты теряются легче всего: пункт выглядит сделанным, PR смержен, борд зелёный — а
проверка, ради которой всё делалось, не проведена.

- Условие пишется **проверяемым командой**, а не памятью.
- ⚠️ **Пункт с невыполненным условием НЕ закрывается в бэклоге.** «Смержено» и «проверено» —
  разные вещи, и раздел заведён ровно из-за этой разницы. Смержённый PR — не основание убрать
  строку отсюда.
- Условие наступило — сказать об этом владельцу **первым делом**, до всего остального.

## 5. Сверка (`refresh`)

Борд врёт легко и незаметно: сессия умерла, ветка смёржена, замок остался занят. Сверяй
**фактами**, а не памятью.

```bash
git worktree list
git branch -a --sort=-committerdate | head -20
gh pr list --repo AutonomaCo/promelectron --state open --limit 20
gh issue list --repo AutonomaCo/promelectron --state open --limit 100 \
  --json number,title,labels,url
git log --oneline -10
```

Если пункт про инфраструктуру — ещё и кластер:

```bash
KUBECONFIG=~/.kube/AutonomaCo kubectl -n promelectron-test get deploy,pods
```

Порядок:

1. Для каждого пункта в «🔵 В работе»: ветка жива? PR открыт или смёржен? Смёржен — закрой
   issue **с доказательством** (номер PR, SHA), убери с борда, освободи замок.
2. «⏰ Ждут условия» сверяй тоже. Условие выполнено и проверка проведена — убирай строку и
   закрывай пункт. Условие выполнено, а проверки не было — строка остаётся, и это надо
   сказать владельцу вслух: именно здесь хвост и теряется.
3. Пересчитай блок «Замки заняты / Свободны» — самое частое расхождение.
4. Синхронизируй с бэклогом: пункты, которых нет в открытых Issues, с борда **убрать**;
   открытые Issues, которых нет на борде, **добавить** (без кнопки, если промпта нет).
5. Обнови шапку: SHA `main` и дату.
6. Прогони проверку формы из раздела 3.

Доска GitHub Project читается токеном со scope `read:project`. Если `gh project …` отвечает
`missing required scopes`, **не молчи**: скажи владельцу выполнить у себя
`gh auth refresh -s project`, а сверку доведи по `gh issue list` + веткам и PR — без колонок
доски, но честно.

## 6. Правила

- **Борд — пульт, а не журнал.** Разборы, замеры и история сюда не пишутся: они живут в
  issue, `.agent/DECISIONS.md`, `.agent/SESSION_LOG.md` и `git log`. Тянет написать абзац
  объяснения — почти наверняка ему место не здесь.
- **Не пересказывай борд целиком.** Владелец умеет читать: дай выжимку и ссылки на якоря.
- **Не выдумывай пункты «для полноты».** Борд из тридцати придуманных задач хуже, чем из
  восьми настоящих: в нём перестают искать.
- **После любой операции с бэклогом синхронизируй борд**, иначе он начнёт врать уже через
  сессию.
- **Правки борда — прямым коммитом в `main`**, поимённо: `git add ai-launcher/BOARD.md`.
  Ревью на борде нет, поэтому проверка формы обязательна.
- **Пункт занимается ДО создания worktree.** Иначе двое возьмут одно и то же.

## 7. Issue и промпт: что где живёт

Это два документа с разными читателями, и путать их дорого в обе стороны. Портянку, написанную
для машины, человек не читает — а короткого человеческого описания агенту не хватает, и он
придумывает задачу сам.

| | GitHub Issue | `ai-launcher/prompts/<замок>_<issue#>-<слаг>.prompt.txt` |
|---|---|---|
| **Читатель** | человек: коллега, вернувшийся через месяц; новый участник | агент: Claude Code, Kimi Code, следующий |
| **Язык** | русский, коротко, без жаргона конвейера | русский, императивно, с точными путями и командами |
| **Содержит** | проблема · почему важно · готово, когда (проверяемо) · где смотреть | где работать · замки · что уже известно · порядок · границы · проверка мутацией · критерий |
| **Не содержит** | worktree, замки, «прогони мутацию», шаги конвейера | обсуждение, историю решений, аргументацию «зачем вообще» |
| **Живёт** | на GitHub — обсуждается, комментируется, закрывается | в `main` — версионируется вместе с кодом, ревьюится в PR |

Шаблон тела issue — `.github/ISSUE_TEMPLATE/task.md`; он же подставляется в веб-интерфейсе
GitHub, так что человек, заводящий задачу руками, получает ту же форму.

### Связка обязательна в обе стороны

**В теле issue** — фиксированный блок внизу:

````markdown
---

### 🤖 Запуск

```bash
make ai PROMPT=ai-launcher/prompts/e2e_186-cart-select-flaky.prompt.txt
```

Промпт лежит в репозитории и одинаково работает у Claude Code, Kimi Code и любого следующего
агента — сама команда задаётся машинно-локально в `Makefile.override.mk`.
````

**В шапке промпта** — номер issue: `Issue #186`. Без него из промпта не найти обсуждение,
и агент работает, не зная, что вокруг задачи уже сказано.

**На борде** — заголовок пункта несёт ссылку на GitHub:
`> <a id="i-186"></a>🟢 **[#186](https://github.com/AutonomaCo/promelectron/issues/186)** · …`,
а строка Указателя — колонку `Issue` со ссылкой. С пульта попадают в две стороны: вниз к кнопке
и наружу в обсуждение.

`scripts/check-board.py` проверяет все три связки и краснеет, если промпт ведёт на закрытый issue.

### Когда пишется промпт

**Не при заведении issue.** Идей в бэклоге всегда больше, чем работы в ближайшей волне, и
промпты к тридцати задачам — выброшенный труд, который к моменту запуска устареет.

Промпт пишется, когда пункт **попадает в волну** — то есть при приоритизации на борде. До этого
пункт живёт в списке «заведено, но кнопки нет», а в блоке «Запуск» стоит строка про `/implement`.

### Кто и когда обновляет issue

Оба агента, по одинаковым правилам:

- **при заведении** — тело по шаблону, человекочитаемо, по-русски;
- **при взятии в работу** — комментарий с номером ветки и ссылкой на PR (карточку двигает конвейер);
- **при закрытии** — комментарий **с доказательством**: номер PR, SHA, вывод прогона. «Сделано»
  без доказательства — это «кажется, сделано»;
- **при отмене** — комментарий, почему пункт больше не нужен, и закрытие `not planned`. Мёртвый
  пункт без объяснения возвращается через полгода как «а почему мы это не сделали».

## 8. Как пайплайн двигает issue в GitHub

Одинаково для Claude Code, Kimi Code и любого следующего агента. Команды — `gh`, репозиторий
`AutonomaCo/promelectron`.

### Метки = замки

Метка зоны на issue **и есть** его замок: `backend` · `frontend` · `e2e` · `infra` · `docs` ·
`harness`. Пункт, трогающий две зоны, несёт две метки. Отсюда `/board refresh` берёт замок, не
угадывая его по названию.

Плюс приоритет (`P0` · `P1` · `P2`) и характер (`security` · `tech-debt` · `bug` ·
`enhancement`).

### Движение по фазам

| Момент | Что делает агент |
|---|---|
| **завёл** | issue по шаблону `.github/ISSUE_TEMPLATE/task.md`, метки зоны + приоритета, строка в Указателе борда |
| **взял в работу** | метка `in-progress`, комментарий с веткой; пункт → 🔵 на борде, замок занят |
| **открыл PR** | метка `in-review` вместо `in-progress`, `Closes #N` в теле PR |
| **смержил** | issue закрывается **с доказательством**, метки статуса снимаются, пункт уходит с борда, замок освобождается |
| **отменил** | закрытие `--reason "not planned"` + комментарий, почему пункт больше не нужен |

```bash
# взял в работу
gh issue edit <N> --repo AutonomaCo/promelectron --add-label in-progress
gh issue comment <N> --repo AutonomaCo/promelectron --body "Взято в работу: ветка \`feature/<task-id>\`."

# открыл PR
gh issue edit <N> --repo AutonomaCo/promelectron --remove-label in-progress --add-label in-review

# закрыл с доказательством
gh issue close <N> --repo AutonomaCo/promelectron --reason completed \
  --comment "Сделано в PR #<PR>, merge \`<SHA>\`. Проверено: <вывод прогона>."
gh issue edit <N> --repo AutonomaCo/promelectron --remove-label in-review

# отменил
gh issue close <N> --repo AutonomaCo/promelectron --reason "not planned" \
  --comment "Снято: <почему больше не нужно, с доказательством>."
```

⚠️ **«Сделано» без доказательства — это «кажется, сделано».** В этом репозитории уже находили
issue, висевший открытым при полностью готовой функции, и запись о «решённом» блокере, чьё
решение было откачено через две недели. Доказательство — номер PR, SHA, вывод прогона.

### Доска GitHub Project — сверху, а не вместо

Колонки Todo / In Progress / In Review / Done ведутся скиллом `github-project` и требуют scope
`read:project` (перемещение — `project`). Если `gh project …` отвечает `missing required scopes`:

1. **не молчи** — скажи владельцу выполнить у себя `gh auth refresh -s project`;
2. **не останавливай работу** — метки `in-progress` / `in-review` несут ту же информацию и
   scope не требуют;
3. на борде отметь, что колонки не сверялись.

Метки — основной путь, доска — витрина поверх него. Так конвейер не встаёт из-за прав токена.
