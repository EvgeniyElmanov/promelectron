## Задача

Миграции применяются дважды: Helm-хуком перед выкатом
(`infra/helm/templates/migrate-job.yaml:9`, `pre-install,pre-upgrade`) и ещё раз на старте
каждого пода (`backend/src/app/main.py:48-65`, lifespan), причём падение на старте глушится
в `logger.warning`. Следствия: гонка `upgrade head` при нескольких репликах (актуально для
#214 — 2 реплики) и молчаливый старт на устаревшей схеме с 500 вместо честного отказа.
Подробности — `gh issue view 217`.

Решение СОГЛАСОВАНО с владельцем (2026-10-06) — вариант A, БЕЗ переключателей:

- Автомиграция из lifespan убирается ПОЛНОСТЬЮ. Никаких env-флагов вида AUTO_MIGRATE —
  обсуждалось и отклонено, поведение кода одно везде.
- Единственное место применения миграций в кластере — Helm-хук (migrate-job.yaml не трогать).
- Локальная разработка накатывает миграции через `make migrate` (цель уже есть, Makefile:120).

## Что уже известно

- `backend/src/app/main.py:48-65` — lifespan: `create_async_engine` + `_run_alembic_migrations`
  через `asyncio.to_thread`, падение проглатывается в warning. Вся эта конструкция уходит.
- `infra/helm/templates/migrate-job.yaml` — Helm-хук `alembic upgrade head`, backoffLimit 3,
  падение Job валит деплой. Это и есть правильное единственное место — НЕ менять.
- Тесты НЕ пострадают: `backend/tests/conftest.py` поднимает app через httpx
  `ASGITransport` — lifespan в тестах не выполняется; схему тесты строят через
  `Base.metadata.create_all` (conftest.py:242), а не через alembic.
- Проверка расхождения схемы: сравнить heads из `alembic.script.ScriptDirectory`
  (`ScriptDirectory.from_config(cfg).get_heads()`) с содержимым таблицы `alembic_version`.
  `alembic current` для этого НЕ подходит — он не падает при расхождении. Отсутствие
  таблицы `alembic_version` (свежая БД без миграций) — тоже расхождение.
- Гейт `migrate-check` (alembic drift, #185) уже перенесён в PR-гейт (#215, смержен) —
  workflow не трогать.

## Порядок

1. Убрать запуск миграций из lifespan в `backend/src/app/main.py` (включая
   `_run_alembic_migrations`, если больше никем не используется).
2. Добавить на старте проверку версии схемы: heads из alembic == `alembic_version` в БД.
   Расхождение или отсутствие таблицы → raise с ПОНЯТНЫМ сообщением, из которого видно
   причину и лечение, например: «Схема БД отстаёт: ожидается revision X, в БД Y (или
   таблица alembic_version отсутствует). В кластере миграции применяет Helm-хук
   migrate-job; локально — make migrate». Под должен честно НЕ стартовать
   (CrashLoopBackOff с этим логом — и есть внятный сигнал).
3. Тесты (pytest): unit-тесты на функцию проверки — схема совпадает → старт проходит;
   revision отстаёт → raise с понятным текстом; таблицы alembic_version нет → raise.
4. Документация локального флоу: в README (раздел про запуск/миграции) явно записать:
   после `git pull` с новыми миграциями api не стартует до `make migrate` — это
   намеренное поведение, а не поломка. Проверь, нет ли ещё мест в docs/, описывающих
   автомиграцию при старте, — приведи к новому поведению.
5. Проверка мутацией (доказательство в PR): локально `alembic stamp <предыдущий revision>`
   на тестовой БД → api отказывается стартовать с внятной ошибкой; `alembic upgrade head`
   → стартует. Приложи вывод обоих прогонов в PR.
