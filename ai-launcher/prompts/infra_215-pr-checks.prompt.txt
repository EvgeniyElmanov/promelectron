## Задача

На pull request не гоняется НИ ОДНА проверка: `grep -rn "pull_request" .github/workflows/`
даёт ноль. PR мержится без единого машинного прогона; первая обратная связь — выкат в общий
test после мержа (инцидент 2026-09-28 с SQLAlchemy обнаружился именно так). Подробности —
`gh issue view 215`.

Задача — PR-gate: backend-тесты, frontend-тесты и линтеры на каждый pull request.
Зона `.github/workflows/` для ЭТОЙ задачи разрешена самим issue — но только она (см. границы).

## Что уже известно

- В `.github/workflows/` четыре файла: `deploy.yml`, `e2e.yml`, `migrate.yml`,
  `cleanup-runner.yml`. `e2e.yml` — только `workflow_dispatch`/`workflow_call` из деплоя.
- Образец фильтрации по путям — `deploy.yml:3-14` (триггеры + `paths`). Держись этой формы.
- Цели Makefile: `make test-backend` (docker compose, postgres+redis, ~8 мин по журналу
  сессий; flock — локальный, на свежем runner безразличен), `make test-frontend` (vitest),
  `make lint` (ruff + oxlint; ruff запинен `==0.15.13` в requirements-dev.txt).
- Гейт `alembic check` (#185) живёт в `deploy.yml` — то есть тоже после мержа. Переносить
  его в PR-гейт НЕ обязательно; если дёшево — можно, реши в spec.
- E2E на PR НЕ требуется критериями issue (дорого; остаётся post-deploy).
- Runner — self-hosted (см. существующие workflows, `runs-on`); образы backend/frontend
  собираются там же, кэш docker-слоёв и pip/npm ускорит прогон.

## Порядок

1. Новый workflow `pr-checks.yml` (НЕ расширять deploy.yml — у него другая роль):
   триггер `pull_request` на main, фильтрация по путям (backend-файлы → backend-job,
   frontend-файлы → frontend-job, workflows/docs — только линтеры или skip).
2. Job'ы: backend (pytest через docker compose, как `make test-backend`), frontend
   (vitest + oxlint), lint (ruff). Кэш pip/npm/docker по образцу существующих workflows.
   Разумное время — требование issue: цель ≤ ~12 мин на полном прогоне.
3. **Доказательство мутацией (критерий issue):** на самом PR с workflow внести временную
   поломку (например, красный assert в тесте backend и frontend по очереди), дождаться
   красного статуса, убрать поломку, дождаться зелёного. Ссылки на оба прогона — в PR.
4. Защита main: включить required status checks через `gh api
   repos/AutonomaCo/promelectron/branches/main/protection` (нужны admin-права токена).
   Нет прав — НЕ молчи: оставь владельцу готовую команду в PR и чекбокс issue отметь
   как «решено не защищать / защищено» с обоснованием.
