## Быстрый старт (первый раз)

### Шаг 1: Выбери режим

| Если ты... | Используй |
|-----------|----------|
| Не знаешь, кто нужен (backend/frontend/devops) | [Orchestrator](#режим-a-orchestrator) |
| Работаешь в одной роли целый день | [Фиксированная роль](#режим-b-фиксированная-роль) |
| Задача охватывает backend+frontend+devops сразу | [Сквозная фича](#режим-c-сквозная-фича) |
| Хочешь полный контроль над ролями | [Диспетчер](#режим-d-диспетчер) |

### Шаг 2: Вставь стартовую команду

**Для Orchestrator (рекомендуется):**
```
Прочитай .agent/ORCHESTRATOR_PROMPT.md и следуй инструкциям.
```

**Для диспетчера:**
```
Прочитай .agent/DISPATCHER_PROMPT.md и следуй инструкциям.
```

### Шаг 3: Напиши задачу

```
Задача: Добавь промокоды в корзину
```

## Ежедневная работа

После первого запуска просто пиши задачи:

```

```

```

```


Система сама определит роль и переключится.

## Режимы работы

### Режим A: Orchestrator (рекомендуется для начинающих)

> Не знаешь роли? Не проблема. Написал задачу — система сама разобралась.

**Как работает:**
1. Orchestrator анализирует твою задачу
2. Определяет нужные роли (backend + frontend + review)
3. Запускает каждую роль через **изолированный Agent tool**
4. Собирает результаты и выводит отчёт

**Преимущество:** каждый Agent работает в своём контексте — **никаких залипаний ролей**.

**Начало сессии (один раз):**
```
Прочитай .agent/ORCHESTRATOR_PROMPT.md и следуй инструкциям.
```

**Все следующие задачи:**
```
Задача: Добавь промокоды в корзину
```

**Когда использовать:**
- Не знаешь, backend это или frontend
- Задача явно смешанная (API + UI)
- Хочешь "написал и забыл"

**Когда НЕ использовать:**
- Нужен жёсткий контроль над каждым шагом
- Задача критичная и требует ручного review после каждого шага

---

### Режим B: Фиксированная роль

> Если целый день только backend (или только frontend) — не нужен диспетчер.

**Начало сессии:**
```
Проект Promelectron. Роль: backend-dev. Задача: Добавь валидацию email в регистрацию.

Прочитай PROJECT_CONTEXT.md, BACKLOG.md, BLOCKERS.md, SESSION_LOG.md.
Прочитай .kimi/agents/backend-dev.md и .kimi/rules/pre-edit-checklist.md.
После работы обнови SESSION_LOG.md.
```

**Все следующие задачи:**
```
Задача: Добавь пагинацию в список заказов
```

> ⚠️ **Важно:** В фиксированной роли смена на другую роль работает плохо. Если понадобилось переключиться — используй Orchestrator.

---

### Режим C: Сквозная фича (cross-cutting)

> Для задач вроде YooKassa E2E → CI/CD → backend → Helm, где одна фича требует работы нескольких ролей последовательно.

**Пример:**
```
Проект Promelectron. Задача: YK-042 — Подключить YooKassa.

Будет затронуто: e2e-tester + backend-dev + devops.
Работай гибко — читай .kimi/agents/<ROLE>.md перед каждым значимым блоком.
Перед правкой кода — .kimi/rules/pre-edit-checklist.md.
После работы обнови SESSION_LOG.md.
```

**Как это работает:**
- Контекст фичи сохраняется между блоками
- Перед каждым блоком агент заявляет: "Сейчас работаю как devops"
- Не нужно перезапускать диспетчера на каждом шаге

**Когда использовать:**
- Одна фича проходит через backend → frontend → devops
- E2E тест → CI/CD pipeline → Helm деплой

**Когда НЕ использовать:**
- Две независимые задачи разных ролей — здесь лучше Orchestrator

---

### Режим D: Диспетчер (ручное переключение)

> Если хочешь контролировать роли сам, но переключать их автоматически.

**Начало сессии:**
```
Прочитай .agent/DISPATCHER_PROMPT.md и следуй этим инструкциям строго.
```

**Все следующие задачи:**
```
Задача: Создай API для промокодов
```

**Что произойдёт:**
1. Kimi выведет `🔄 Диспетчер: сброс роли...`
2. Определит роль по ключевым словам
3. Прочитает `.kimi/agents/<ROLE>.md`
4. Выполнит задачу

**Надёжность:** ~70–90% в длинной сессии. Если "залип" — используй Orchestrator или новую сессию.

## Работа через терминал IDE

Всё работает через Python — никакого bash.

### Вариант 1: Через `make` (рекомендуется)

```bash
# Авто-определение ролей
make auto MSG="Добавь промокоды в корзину"

# С гарантированным сбросом роли
make ask MSG="Сделай страницу checkout"

# Роутер с контекстом
make task MSG="Создай API для промокодов"
```

### Вариант 2: Через Python напрямую

```bash
python3 scripts/kimi.py auto  "Добавь промокоды в корзину"
python3 scripts/kimi.py task  "Создай API для промокодов"
python3 scripts/kimi.py ask   "Сделай страницу checkout"
```

### Вариант 3: Через VS Code Tasks

Нажми **Ctrl+Shift+P** → **Tasks: Run Task** → выбери:

| Задача | Что делает |
|--------|-----------|
| `Kimi: Auto` | Авто-определение ролей, запросит текст задачи |
| `Kimi: Task` | Роутер с полным контекстом |
| `Kimi: Ask` | Гарантированный сброс роли |
| `Dev: Запустить стек` | `make dev` |
| `Test: Backend` | `make test-backend` |
| `Agent: Audit системы` | Проверка целостности агентов |

> Файл задач: `.vscode/tasks.json`

## Формат задачи (5 элементов)

Чем конкретнее задача — тем лучше результат.

```
[РОЛЬ] Задача: [что сделать, одно предложение]
Файл: [конкретный файл или зона]
Рядом: [связанные файлы, которые тоже затронутся]
Нельзя ломать: [что трогать нельзя]
Проверь: [как убедиться, что работает]
```

### Примеры

**Backend:**
```
[backend-dev] Задача: Добавить поле promo_code в модель Order
Файл: backend/src/app/models/order.py
Рядом: backend/src/app/schemas/order.py, backend/src/app/services/order_service.py
Нельзя ломать: существующие миграции, таблицу payments
Проверь: pytest tests/test_orders.py && ruff check backend/src/app/models/order.py
```

**Frontend:**
```
[frontend-dev] Задача: Добавить поле ввода промокода в Cart.vue
Файл: frontend/src/views/Cart.vue
Рядом: frontend/src/services/cart.js, frontend/src/stores/cart.js
Нельзя ломать: существующий расчёт итоговой суммы, мобильную вёрстку
Проверь: npm run test:unit Cart && проверь адаптивность (375px)
```

**DevOps:**
```
[devops] Задача: Добавить YOOKASSA_SECRET_KEY в Helm secrets
Файл: infra/helm/templates/secrets.yaml
Рядом: infra/helm/values.yaml, .env.example
Нельзя ломать: существующие секреты (DATABASE_URL, JWT_SECRET)
Проверь: helm template . | grep -A5 yookassa
```

> Подробнее — в `.kimi/rules/prompt-format.md`

## Что делать после задачи

Агент **обязан** обновить:

1. **`.agent/SESSION_LOG.md`** — что сделано, файлы, риски
2. **`.agent/BACKLOG.md`** — статус задачи (если из спринта)
3. **`.agent/BLOCKERS.md`** — новые блокеры (если появились)
4. **`PROJECT_CONTEXT.md`** — если архитектура изменилась

**Проверь перед отчётом:**
- [ ] Тесты проходят (`make test`)
- [ ] Линт чистый (`make lint`)
- [ ] Критичные сценарии не сломаны (`.kimi/rules/golden-path.md`)

## Если что-то пошло не так

### Orchestrator / Диспетчер "залип" — не сменил роль

**Признаки:**
- Нет строки `🔄 Диспетчер: сброс роли...`
- Агент отвечает в стиле предыдущей роли (backend пишет Vue)

**Решения (по надёжности):**

1. **Orchestrator (100% надёжно):**
   ```
   Прочитай .agent/ORCHESTRATOR_PROMPT.md и следуй инструкциям.
   Задача: <...>
   ```

2. **Явное указание роли:**
   ```
   Роль: frontend-dev. Задача: Сделай страницу checkout
   ```

3. **Новая сессия Kimi CLI**

### Система выбрала не ту роль

**Решение:** Уточни формулировку или укажи роль явно:
```bash
make ask MSG="[frontend-dev] Сделай страницу checkout"
```

### Хочу две независимые задачи разом

**Не пиши:** `Сделай API и исправь Helm`

**Пиши двумя сообщениями:**
```
Задача: Создай API для X
```
```
Задача: Исправь Helm шаблон для Y
```
