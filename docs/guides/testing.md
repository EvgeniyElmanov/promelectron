# Правила для тестировщика (E2E & Integration)

> ## ℹ️ Правила писались для человека-тестировщика
>
> На момент переноса в `docs/` на этот файл **не ссылался ни один другой документ**.
> Рабочие правила тестирования живут в скиллах: `.kimi-code/skills/qa/`,
> `.agents/agents/e2e-tester.md`, `.agents/skills/testing-conventions/`.
> Здесь сохранён сквозной чек-лист «проверь полный путь пользователя» — он не покрыт скиллами
> и остаётся полезным. Расхождение со скиллами решается в пользу скиллов.


> После КАЖДОЙ фичи обязательно пройти этот чек-лист. Не считать фичу готовой, пока не выполнены все пункты.

---

## 1. Золотое правило: проверять сквозной сценарий (End-to-End)

После любого изменения в backend ИЛИ frontend обязательно проверить **полный путь пользователя** от начала до конца.

**Пример бага, который должен был быть пойман:**
> Фича "Регистрация поставщика" — backend разрешил роль `supplier`, но не создал запись в таблице `suppliers`. При попытке создать товар — ошибка `You are not registered as a supplier`. Это должен был поймать E2E-тест на создание товара после регистрации.

## 2. Чек-лист после каждой фичи

### 2.1 Backend API — проверить ВСЕ роли

| Роль | Что проверить |
|------|--------------|
| **Гость (без токена)** | Должен получить 401/403 на защищённых эндпоинтах |
| **Покупатель (`user`)** | Доступны: каталог, корзина, заказы, профиль, отзывы, избранное. НЕ доступно: создание товаров, админка |
| **Поставщик (`supplier`)** | Доступно: создание/редактирование СВОИХ товаров, "Мои товары". НЕ доступно: админка, чужие товары |
| **Админ (`admin`)** | Доступно: админ-панель, управление пользователями, все товары |

**Критично:** если фича добавляет новую ролевую проверку — протестировать ВСЕ 4 роли!

### 2.2 Frontend — проверить ВСЕ кнопки и состояния

- [ ] **Happy Path** — основной сценарий работает (например: зарегистрировался → создал товар → товар отображается в каталоге)
- [ ] **Пустое состояние** — нет данных, показывается ли заглушка?
- [ ] **Ошибки сети** — выводится ли понятное сообщение?
- [ ] **Валидация форм** — пустые поля, слишком длинные, невалидный email, отрицательные числа
- [ ] **Загрузка (loading)** — показывается ли skeleton/spinner?
- [ ] **Успех** — после успешного действия: toast-уведомление, редирект, обновление данных

### 2.3 Проверить связанные фичи

Новая фича могла сломать старые. Обязательно проверить:

```
Если менял:                То проверь:
─────────────────────────────────────────────
Регистрация/Авторизация    →  Весь личный кабинет, корзина, заказы
Модель Product             →  Каталог, корзина, заказы, поиск, фильтры
Модель Order               →  Заказы, оплата, уведомления, email
Модель User                →  Все страницы с авторизацией, админка
API ответ (формат)         →  Все страницы, которые его используют
```

### 2.4 Проверить мобильную версию

- [ ] Страница не ломается на ширине 375px (iPhone SE)
- [ ] Кнопки достаточно большие для пальца
- [ ] Нет горизонтальной прокрутки
- [ ] Нижняя навигация работает

## 3. E2E сценарии — обязательные для каждой фичи

### Сценарий A: Регистрация и первая операция
```
1. Открыть сайт как гость
2. Зарегистрироваться (проверить все роли, если применимо)
3. Выполнить ключевое действие этой роли:
   - Покупатель: добавить товар в корзину
   - Поставщик: создать товар
   - Админ: открыть админку
4. Убедиться, что действие успешно и данные сохранились
```

### Сценарий B: Полный цикл покупки
```
1. Зарегистрировать поставщика → создать товар
2. Зарегистрировать покупателя → найти товар → добавить в корзину
3. Оформить заказ → оплатить (mock) → проверить статус
4. Проверить уведомления у обоих пользователей
```

### Сценарий C: Фильтры и поиск
```
1. Создать 5+ товаров с разными ценами, категориями, рейтингами
2. Применить каждый фильтр по отдельности
3. Применить комбинацию фильтров
4. Проверить сортировку во всех направлениях
5. Проверить пагинацию (показать ещё / бесконечный скролл)
```

## 4. Типичные баги — ловушки

| Баг | Как ловить | Пример |
|-----|-----------|--------|
| **Разъезд API и frontend** | Backend меняет формат ответа, frontend ожидает старый | `List[Product]` → `{"items": [], "total": 0}` |
| **Нет проверки роли** | Поставщик может зайти в админку по прямой ссылке | `GET /admin` с токеном supplier должен редиректить |
| **Нет eager loading** | SQLAlchemy lazy load в async → `MissingGreenlet` | Всегда `selectinload()` при возврате связанных сущностей |
| **Забыли про пустые данные** | Пустой список → белый экран вместо заглушки | `products.length === 0` → показать "Товары не найдены" |
| **Забыли про ошибки** | 500 ошибка → непонятное сообщение | Показать "Не удалось загрузить товары" + кнопка retry |
| **Несоответствие данных** | Создали в БД, но в UI не отображается | Проверить `created_at`, кеш, refetch |

## 5. Инструкция по запуску проверки

### Быстрая проверка (5 мин)
```bash
# 1. Запустить проект
make dev          # или: docker compose up -d + uvicorn + npm run dev

# 2. Запустить все тесты
make test         # backend pytest
make frontend-test # frontend vitest
```

### Полная E2E проверка (15 мин)
```bash
# 1. Убедиться что проект запущен на http://localhost:5173

# 2. Запустить Playwright тесты
make test-e2e

# 3. Если нет E2E теста на новую фичу — написать и запустить:
cd tests/e2e && npx playwright test --headed
```

### Ручная проверка через UI
Если автотестов недостаточно — открыть браузер и пройти чек-лист из раздела 2.

## 6. Playwright E2E — шаблон нового теста

При добавлении новой фичи писать такой тест:

```typescript
// tests/e2e/features/new-feature.spec.ts
import { test, expect } from '@playwright/test';

test.describe('Название фичи', () => {
  test.beforeEach(async ({ page }) => {
    // Подготовка: регистрация, логин, создание данных
  });

  test('happy path', async ({ page }) => {
    // Шаг 1
    // Шаг 2
    // Ожидание результата
    await expect(page.locator('[data-testid="result"]')).toContainText('Успех');
  });

  test('ошибка: неавторизован', async ({ page }) => {
    // Проверка 401/403
  });

  test('пустое состояние', async ({ page }) => {
    // Проверка заглушки
  });
});
```

## 7. Определение готовности

Фича считается **готовой** только если:

- [ ] Все backend тесты проходят (`pytest -x`)
- [ ] Все frontend тесты проходят (`vitest run`)
- [ ] E2E тест на happy path проходит
- [ ] Проверен хотя бы 1 edge case (ошибка, пустое состояние)
- [ ] Проверены все роли, которых касается фича
- [ ] Не сломаны существующие фичи (все тесты зелёные)

---

> **Помни:** автотесты ловят 80% багов, но оставшиеся 20% — только ручная проверка полного сценария. Не ленись пройтись по кнопкам!
